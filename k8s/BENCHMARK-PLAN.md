# Squid 上限压测计划（待确认后执行）

> 目标：通过提高并发 N，找出配置的**上限拐点**——副本数、CPU、内存的饱和点，
> 反哺 `../sizing/SQUID-SIZING-K8S.md` 的规格推导逻辑。
> **本文档需你确认后再执行压测。**

## 0. 策略：小规格摸上限（省时省资源）

摸上限不需要大规格。**故意把 Squid 调小**，用**小 N** 就能快速触顶，大幅减少测试时间与集群压力：

| 项 | 压测规格(调小) | 原因 |
|----|--------------|------|
| 单副本 CPU limit | **200m** | 小 CPU 配额,几十并发即可打满 → 快速看 CPU 拐点 |
| 单副本内存 limit | **128Mi** | 小内存,缓存/SSL 上下文很快触及 → 快速看 OOM |
| 副本数 | **1-2** | 单副本饱和即可推导,不追求大规模 |
| N 扫描 | **10 → 20 → 40 → 80**(小步) | 小规格下小 N 就触顶 |
| cache_mem | 调小(如 64MB) | 配合小内存 |

思路：**先把单副本压到饱和(CPU 打满 或 OOM)记录拐点 N**,再看副本数如何线性放大,
最后把小规格的拐点数据外推校准 sizing 公式。

## 1. 已有校准数据（N=20 基线）

| 指标 | 实测值 | 说明 |
|------|--------|------|
| 单流缓存命中吞吐 | **~90 MB/s (720 Mbps)** | 集群内 HIT 服务速度 |
| 命中延迟(14MB对象) | **0.165s** | 纯 HIT |
| 回源(MISS)速度 | 1-3 MB/s，最高 13.6s | 受 openEuler 源站限速 |
| 热缓存并发命中率 | **95%** (38/40) | 缓存已填充 |
| 冷启动并发命中率 | **55%** (18/33) | 首波并发同时 MISS(collapsed forwarding 退化) |
| N=20 时 Squid 用量 | **CPU 58m / 内存 49Mi** | 配额 1核/1Gi，**利用率仅 6%/5%** |

**结论**：N=20 远未压满，Squid 资源利用率极低。当前瓶颈在**并发数/源站带宽**，非 Squid 本身。
要找上限必须大幅提高 N 并系统加压。

## 2. 压测目标（找三个上限）

| 上限 | 问题 | 观测信号 |
|------|------|---------|
| **副本数上限** | 多少副本能扛住目标 N？单副本承载多少并发流？ | 单副本饱和时的 N/吞吐 |
| **CPU 上限** | Squid 何时 CPU 打满(单核瓶颈)？ | `kubectl top` CPU 接近 limit |
| **内存上限** | 何时 OOMKilled？SSL 上下文/索引增长曲线 | 内存接近 limit / OOM 事件 |

## 3. 关键约束与设计决策

### 3.1 绕开 csi-disk 的 AZ 限制（副本数测试的前提）
- 现状：csi-disk 是 `Immediate` 绑定的多 AZ 存储，第 3 副本因 AZ 冲突 Pending。
- 对策：**副本数上限测试改用 Deployment + emptyDir**（无 PVC，可自由调度到任意节点），
  这样能把副本数从 2 拉高到 N 个测真实上限。
- StatefulSet+PVC 版保留用于"持久化"功能验证，不用于副本上限压测。

### 3.2 隔离源站带宽变量
- MISS 受 openEuler 源站限速（1-3 MB/s），会掩盖 Squid 真实能力。
- 对策：**先预热缓存**（跑一轮填充），再压测**纯 HIT 场景**——测 Squid 的服务上限而非源站。
- 另设一组**冷启动压测**，专门量化"冷启动出向带宽峰值"（校准 sizing 报告的冷启动余量系数）。

### 3.3 提高并发 client 侧
- client 用 Job parallelism 拉起，N 从 20 → 50 → 100 → 200 → 400 递增。
- 注意 client Pod 本身占集群资源，大 N 时 client 也要够节点调度。

## 4. 测试矩阵（小规格·小 N）

### 阶段 A：单副本饱和点（1 replica, CPU 200m/内存 128Mi, 纯 HIT）
预热后固定 1 小副本, N 小步递增, 找 CPU 打满或成功率下降的拐点：

| 轮次 | N(并发) | 观测 |
|------|---------|------|
| A1 | 10 | 基线 |
| A2 | 20 | |
| A3 | 40 | CPU 接近 200m limit? 单流吞吐下降? |
| A4 | 80 | 找拐点(成功率/延迟劣化) |

每轮记录：成功率、单流吞吐(min/avg/max)、Squid CPU、Squid 内存、错误类型。
→ 得出**小规格单副本的 N_max 与吞吐 P_small**。

### 阶段 B：副本线性扩展（emptyDir, 固定饱和 N）
用 A 阶段的饱和 N, 副本 1→2 验证是否翻倍：

| 轮次 | 副本数 | 观测 |
|------|--------|------|
| B1 | 1 | 单副本吞吐(参照) |
| B2 | 2 | 吞吐是否~2×; ClientIP 亲和去重效果 |

→ 验证 `K = B_in / P` 的线性假设(小规模足够证明趋势)。

### 阶段 C：资源拐点（CPU/内存）
固定 1 副本 + 饱和 N, 调资源档看拐点：

| 轮次 | CPU limit | 内存 limit | 观测 |
|------|-----------|-----------|------|
| C1 | 200m | 128Mi | 基线(小) |
| C2 | 100m | 64Mi | 更小 → CPU 节流/OOM 更早出现 |
| C3 | 500m | 256Mi | 放大 → N_max 提升多少 |

→ 校准**单副本 CPU/内存推导系数**(小规格数据外推)。

### 阶段 D：冷启动出向峰值（校准冷启动余量）
清缓存 → 饱和 N 并发 → 测冷启动命中率与回源量,
量化"冷启动出向 = B_in ×(1−冷启动命中率)"的真实系数。
(此阶段与规格无关, N 用 A 的饱和值即可)

## 7. 风险与边界

- 大 N（200+）会给测试集群/源站压力，需你确认可承受
- client Pod 数量受集群节点/配额限制，超大 N 可能 client 侧先瓶颈
- 源站带宽是外部变量，纯 HIT 测试已隔离，但冷启动测试受其影响
