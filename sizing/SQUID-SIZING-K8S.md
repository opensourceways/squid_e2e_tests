# Squid 生产规格与 Kubernetes 部署调研报告

> 目标：为在 Kubernetes 中以 Deployment/StatefulSet 部署 Squid 集群提供**规格量化**与
> **副本/配置预管控**依据。覆盖网络出入带宽、磁盘（IO/容量/缓存策略配合）、CPU、内存、
> 缓存策略、以及 K8s 部署关键点。
>
> 证据分级：**[实测]** 来自公开基准；**[经验]** 业界经验法则；**[推导]** 由公式推算。
> 具体数字务必用你自己的流量画像做压测校准——Squid 性能对工作负载极敏感。

---

## 0. 一页速查（先看这个）

| 维度 | 规格经验值 | 关键约束 |
|------|-----------|---------|
| **CPU** | 1 核 ≈ 30-80 Mbps（普通代理）；**SSL Bump 减半** | 单 worker 单核瓶颈，SMP 最多 ~28-30 worker |
| **内存** | 索引 10-20 MB / GB 磁盘缓存 + `cache_mem` 热对象 + SSL 上下文缓存(可达 GB) | 内存不足会 swap，性能雪崩 |
| **磁盘容量** | = 日活工作集 ÷ 目标命中率；预留 **20% 空闲** | 用满 >80% 性能骤降 |
| **磁盘 IO** | 机械 100-400 随机 IOPS/盘；**小块随机 IO，看 IOPS/寻道不看吞吐** | SSD 比 HDD 快 10x+；多小盘各一个 cache_dir |
| **入向带宽** | 可达近线速（LAN ~980 Mbps 单实例[实测]） | 按客户端峰值需求配 |
| **出向带宽** | = 入向 ×(1 − 命中率) | 命中率 60-92%，出向可省 60-92% |

## 1. 网络出入带宽（重点）

Squid 的**入向**（客户端→Squid）和**出向**（Squid→源站）带宽是**非对称**的，这是缓存的核心价值，也是 K8s 里最容易配错资源的维度。

### 1.1 双向带宽模型

```
客户端 ──入向 B_in──> Squid ──出向 B_out──> 源站
                        │
                   命中率 H
                        │
        B_out = B_in × (1 − H)      ← 缓存削减出向带宽
        出向节省 = B_in × H          ← 这就是缓存省的钱
```

| 命中率 H | 出向带宽 B_out（相对入向） | 出向节省 |
|---------|------------------------|---------|
| 60% | 40% | 60% |
| 85%（优化后静态内容[经验]） | 15% | 85% |
| 92%（视频/包镜像优化[经验]） | 8% | 92% |

**含义**：如果你的集群客户端峰值需求是 10 Gbps 入向，命中率 85%，那么**出口（到源站/公网）只需约 1.5 Gbps** + 余量。这直接决定：
- Pod 的 **入向 NIC/带宽**要按客户端峰值配（可能很大）
- **集群出口带宽/NAT/防火墙**按 `入向 ×(1−H)` 配（小很多）——这是缓存代理的省钱点

### 1.2 单实例带宽能力 [实测]

- LAN 侧（入向）配置得当可达近线速 **~980 Mbps**（Squid 2.7 实测）
- 现代 4 核 trunk 版持续 **313 Mbit/s**（受 CPU 而非网卡限制）
- 出向 ~40 Mbit/s ≈ ~1000 RPS（旧版实测参考量级）

### 1.3 规格要点

- **入向带宽**按客户端**峰值并发**需求配，不是均值——突发（如全集群同时拉镜像/更新）是峰值来源
- **出向带宽**=入向×(1−命中率)+安全余量（冷启动、缓存未命中风暴时出向会短时逼近入向）
- **冷启动风险**：Pod 刚起、缓存空时命中率 0%，出向 = 入向。滚动更新/扩容时多个冷 Pod 会让出向短时飙升——**出口带宽要留冷启动余量**
- K8s 里若用 CNI 带宽限制（`kubernetes.io/ingress-bandwidth`）要同时约束入向和出向，避免限死出向导致回源阻塞

## 2. 磁盘（IO + 容量 + 缓存策略配合）

磁盘是 Squid 的**首要性能瓶颈**。要分三层看：容量、IO 特征、与缓存策略的配合。

### 2.1 IO 特征：小块随机 IO，看 IOPS 不看吞吐 [实测]

> Squid 读写的数据块很小，**寻道时间/IOPS 比吞吐量重要**。

| 存储 | 随机 IOPS | 适用 |
|------|-----------|------|
| 机械盘 5.4k/7.2k | 100-200 | 小规模/预算受限 |
| 机械盘 15k | 300-400 | 中规模 |
| **SSD** | 数万+ | **中大规模推荐（比 HDD 快 10x+）** |

**IO 与流量的关系** [经验]：约每 **8 Mbps 可缓存流量需 1 个 HDD 主轴** 的随机 IO 能力。SSD 可大幅合并。

### 2.2 容量 sizing [推导]

```
磁盘容量 = 期望缓存的工作集大小 ÷ 目标命中率的边际收益点
```
实践：容量越大命中率越高，但边际递减。先按"覆盖 N 天热点工作集"估，再用命中率曲线校准。

**硬约束**：
- **预留 20% 空闲** [实测]——文件系统用满 >80% 性能骤降
- 单 `cache_dir` 目录树 = `L1 × L2`（如 `16 × 256`）分散文件，避免单目录文件过多

### 2.3 缓存策略配合（磁盘规格与 squid.conf 联动）

| 指令 | 作用 | 与规格的联动 |
|------|------|------------|
| `cache_dir aufs /path 容量MB L1 L2` | 磁盘缓存后端与容量 | **JBOD：每物理盘一个 cache_dir，不做 RAID** [实测]。SMP 模式必须用 `rock` |
| `maximum_object_size 4 GB` | 单对象上限 | 缓存镜像/RPM/ISO 等大文件要调大，否则大对象不缓存→出向带宽省不下来 |
| `cache_mem 4096 MB` | 内存热对象缓存 | 命中内存的对象**完全不碰磁盘**→降低磁盘 IOPS 压力 |
| `cache_replacement_policy heap LFUDA` | 磁盘替换策略 | **LFUDA 最大化字节命中率→最省出向带宽**（大文件场景首选） |
| `memory_replacement_policy heap GDSF` | 内存替换策略 | **GDSF 最大化对象命中率→最省磁盘 IOPS** |
| `refresh_pattern` | freshness 规则 | 对 RPM/包镜像等不变内容设长 TTL，直接提升命中率 |

**策略选择速记**：
- 省**出向带宽**（大文件/镜像源）→ 磁盘用 **LFUDA** + 调大 `maximum_object_size`
- 省**磁盘 IOPS**（小文件/高并发）→ 内存用 **GDSF** + 加大 `cache_mem`
- 默认 **LRU** 均衡，CPU 开销最低

### 2.4 K8s 存储要点

- cache_dir 落在 **块存储 PVC（RWO）**，storageClass 选 **SSD/高 IOPS**
- **禁用 NFS/共享文件系统做 cache_dir**——Squid 需要 POSIX 语义 + 低延迟，NFS 会拖垮
- 每 Pod 独立 PVC（见 §6 StatefulSet）

## 3. CPU

### 3.1 单核吞吐 [实测/经验]

| 场景 | 单核吞吐 |
|------|---------|
| 普通转发代理 | ~30-80 Mbps/核（现代 Xeon，受 ACL/日志影响） |
| **SSL Bump（HTTPS 解密）** | **约减半**——双向 TLS 加解密翻倍 CPU [经验] |
| 峰值 | 1-3 核满载即达单实例上限 [实测] |

### 3.2 关键约束

- Squid **单 worker 单核**处理请求；多核靠 **SMP `workers N`**，但：
  - 每非超线程物理核 1 worker，**64 核最多约 28-30 worker**（协调开销抵消收益）[经验]
  - 超线程对 Squid 收益不大
  - SMP 模式 cache_dir 必须用 `rock`（aufs/diskd 在 SMP 下会损坏）
- SSL Bump 是 CPU 大头——**如果集群大量 HTTPS 缓存，CPU 要按 Bump 减半后估**

### 3.3 K8s：SMP worker vs 多副本

**推荐在 K8s 里用多 Pod 副本，而非单 Pod 内堆 SMP worker**：
- K8s 天然管理 Pod 生命周期/调度/探针，副本更符合云原生
- 单 Pod 给 1-4 核 + 1-4 worker 即可，再横向扩副本
- 代价：**每 Pod 独立缓存→跨副本缓存重复**（见 §5 命中率联动）

## 4. 内存

### 4.1 内存构成（三块，都要算）

| 内存块 | 大小 | 说明 |
|--------|------|------|
| **索引** | **10-20 MB / GB 磁盘缓存** [实测] | 每个缓存对象占 76-112 字节内存；磁盘越大索引越大 |
| **`cache_mem` 热对象** | 按需（如 4 GB） | 命中内存的对象不碰磁盘 |
| **SSL 上下文缓存** | **可达数 GB** | SSL Bump 为每个域名缓存 SSL_CTX，`dynamic_cert_mem_cache_size` 控制但有已知不精确 |

### 4.2 sizing 公式 [推导]

```
Pod 内存 ≈ (磁盘缓存GB × 15MB) + cache_mem + SSL上下文缓存 + 缓冲/余量
```
例：1 TB 磁盘缓存 → 索引约 15 GB；再加 cache_mem 4 GB + SSL 2 GB + 余量 → **~24 GB/Pod**。

### 4.3 关键约束

- **内存不足会 swap → 性能雪崩**，比 CPU/磁盘不足更致命
- K8s **`resources.limits.memory` 要足够**，否则 OOMKilled；SSL Bump 场景尤其要给 SSL 上下文留量
- `requests` ≈ 稳态用量，`limits` ≈ 稳态 + SSL 峰值余量，避免频繁 OOM

## 5. 缓存命中率与规格的联动（贯穿性）

命中率 H 不是独立参数，它同时决定**出向带宽**、**磁盘 IOPS**、**回源延迟**，且被**磁盘容量/内存/替换策略/副本数**共同影响。

```
磁盘容量↑ → 缓存更多 → H↑ → 出向带宽↓
cache_mem↑ → 内存命中↑ → 磁盘IOPS↓
副本数↑（无 CARP）→ 缓存分散重复 → 单副本有效缓存↓ → H↓
替换策略 → LFUDA 提字节命中(省带宽) / GDSF 提对象命中(省IOPS)
```

**副本与命中率的权衡（K8s 关键）**：
- 简单多副本（LB round-robin/random）→ 同一对象在多副本各存一份→**有效缓存 = 总容量 ÷ 重复因子**，命中率下降
- 要保命中率 → 前置 LB 用 **一致性哈希（consistent hashing）/ CARP**，让同一 URL 固定路由到同一副本，实现**去重**（见现有方案 `../solution.md` 的 `balance source` / CARP 讨论）
- **结论**：副本数不是越多越好；扩副本要配合哈希路由，否则命中率被稀释、出向带宽反弹

## 6. Kubernetes 部署关键点

### 6.1 Deployment vs StatefulSet（核心决策）

| 维度 | Deployment（缓存易失） | StatefulSet（缓存持久） |
|------|----------------------|----------------------|
| 存储 | `emptyDir` 或临时盘 | **每 Pod 独立 PVC（volumeClaimTemplates）** |
| Pod 身份 | 随机名，无序 | 稳定名 + 稳定 PVC 绑定 |
| 重启后缓存 | **丢失（冷启动）** | **保留（PVC 复用）** |
| 适用 | 缓存可快速重建、追求简单弹性 | 大缓存、冷启动代价高、要持久化 |

**决策依据**：Squid 缓存**可自愈**（内容有 TTL，丢了回源重拉，不是数据丢失）。所以：
- **缓存小 / 命中率要求不高 / 追求弹性** → **Deployment + emptyDir**，重启冷缓存可接受
- **缓存大（TB 级）/ 冷启动回源风暴代价高 / 要跨重启保温** → **StatefulSet + PVC**

> ⚠️ StatefulSet 的隐性成本：Pod 重启后 Squid 要**重建 `swap.state` 索引**，TB 级缓存可能耗时数分钟到数十分钟（见 §6.3 启动探针）。

### 6.2 副本、反亲和、去重

- **副本数**：按 §1 入向带宽峰值 ÷ 单副本吞吐（§3 CPU 约束）估，留冷启动/故障余量
- **Pod 反亲和**（`podAntiAffinity`）：把副本打散到不同 node，避免单 node 故障带走多副本
- **去重路由**：前置 Service/LB 用会话亲和或一致性哈希（见 §5），否则副本越多命中率越低

### 6.3 探针（Squid 特有注意点）

| 探针 | 建议 | 原因 |
|------|------|------|
| **startupProbe** | TCP 3128，**failureThreshold 放大**（覆盖缓存重建时间） | 大缓存重建 `swap.state` 耗时长，否则启动即被 liveness 杀死 |
| **readinessProbe** | 经代理发一个真实请求（HTTP 200）或 TCP 3128 | 确认 Squid 真能代理，未就绪不进 LB |
| **livenessProbe** | TCP 3128 | 进程挂了才重启；不要用重请求以免误杀 |

> 关键坑：**没有 startupProbe 或阈值太小 → 大缓存重建期间被 liveness 反复杀 → 永远起不来**。

### 6.4 滚动更新对缓存的影响

- 每个新 Pod 起来是**冷缓存** → 滚动更新期间**命中率整体下探、出向带宽上冲**
- `maxSurge` 设正值先起新 Pod（暖起来）再下旧的，减少命中率断层
- `maxUnavailable=0` + `maxSurge>0` 保证容量不降，但要有出向带宽余量扛冷 Pod
- StatefulSet 滚动更新是**有序**的，缓存冲击更平缓但更慢

### 6.5 资源 requests/limits

- 按 §3/§4 的 CPU/内存 sizing 设
- **memory limit 给足 SSL 上下文峰值**，否则 SSL Bump 场景易 OOMKilled
- CPU limit 不宜过低——Squid 单请求延迟对 CPU 节流敏感

### 6.6 HPA（自动扩缩）的注意

- 可按 CPU/连接数扩，但**扩出来的是冷缓存副本**，短期命中率降、出向升
- 缩容会**永久丢弃该副本缓存**
- HPA 对缓存类服务要**保守**（长冷却、下限副本数够高），或干脆固定副本 + 手动扩

### 6.7 配置与日志

- `squid.conf` 用 **ConfigMap** 挂载；改配置滚动重启（注意 §6.4 冷缓存冲击）
- SSL Bump 的 **CA 证书/密钥用 Secret** 挂载
- **access.log 量极大**（高流量每天数 GB）→ 输出到 stdout + 节点日志采集，或 sidecar 轮转；不要写进 PVC 撑爆缓存盘

## 7. 驱动模型：从业务输入推算全部规格（核心）

前面各维度是"知识"，本节把它们收敛成**一条可套用的推算链**：先确定工作负载类型，
再用**少数几个你实际知道的业务输入**，推出每一个规格参数。

### 7.1 第一步：确定工作负载类型（决定瓶颈在哪）

| 类型 | 特征 | 瓶颈 | 单核吞吐 | 你的场景 |
|------|------|------|---------|---------|
| **A. 小对象网页缓存** | 海量小请求，高 RPS | **CPU(RPS) + 磁盘随机 IOPS** | 30-80 Mbps/核 | 通用上网代理 |
| **B. 大文件/包镜像缓存** | 少量大下载(包/层/ISO)，高字节流 | **出入带宽 + 磁盘容量/顺序吞吐** | 数 Gbps/核(AES-NI crypto-bound) | ✅ **BuildKit/包缓存** |

> **关键分野**：大文件场景 CPU **不是**瓶颈（带 AES-NI 的 TLS 批量加解密可达每核数 Gbps），
> 即使开 SSL Bump，CPU 也很少成为限制——**瓶颈是带宽与磁盘容量/IOPS**。
> 所以你的场景可以用「**并发下载数 + 缓存失效天数**」作为主驱动输入（正是你的直觉）。

### 7.2 第二步：业务输入（你实际知道的量）

以 **B 类（BuildKit/包缓存）** 为例，只需 6 个输入：

| 符号 | 含义 | 示例值 |
|------|------|--------|
| `N` | **峰值并发下载流数** | 200 |
| `v` | 单流目标速率（客户端体验下限） | 50 Mbps |
| `s` | 平均对象大小（包/层） | 50 MB |
| `d` | 日新增唯一内容量 | 20 GB/天 |
| `R` | **缓存保留/失效天数** | 7 天 |
| `H` | 目标命中率 | 0.85 |

### 7.3 第三步：推算链（输入 → 每个规格）

| 规格 | 公式 | 算例结果 |
|------|------|---------|
| **入向峰值带宽** `B_in` | `N × v` | 200 × 50 = **10 Gbps** |
| **出向峰值带宽** `B_out` | `B_in × (1−H)` ，**× 2 留冷启动余量** | 10 × 0.15 × 2 = **3 Gbps** |
| **总缓存容量** `Disk` | `(d × R) ÷ 0.8`（保留 20% 空闲） | (20×7)/0.8 = **175 GB** |
| **峰值并发连接/FD** | `N × 2`（每流 client+server）+ 余量 | 200×2 → `max_filedescriptors` ≈ **1024+** |
| **副本数** `K` | `ceil(B_in ÷ P) + 故障余量`，`P`=单副本可持续吞吐(压测) | ceil(10000/1000)+2 = **12** |
| **单副本磁盘** | `Disk ÷ K`（**前提：一致性哈希去重**） + 20% | 175/12 ≈ **18 GB/副本** |
| **单副本内存** | `单副本磁盘GB × 15MB + cache_mem + SSL余量` | 18×15MB + 1GB + 1GB ≈ **2.3 GB/副本** |
| **单副本 CPU** | B 类 crypto-bound：`B_in/K ÷ 每核Gbps` | 0.83Gbps ÷ ~2Gbps/核 ≈ **1 核**（给 2 核余量） |
| **磁盘类型/IOPS** | 峰值并发 miss = `N×(1−H)`，随机小 IO → **SSD** | 30 并发 miss → SSD(数万 IOPS)绰绰有余 |

> **`R`（缓存失效天数）直接驱动磁盘容量**：`Disk = d×R/0.8`。保留越久命中率越高但盘越大——
> 这是你「按缓存失效天数算」的核心链路。
> **`N`（并发数）直接驱动带宽、连接数、副本数**：`B_in=N×v`、`FD=N×2`、`K=B_in/P`。

### 7.4 第四步：部署形态

| 判据 | 选择 |
|------|------|
| 单副本磁盘小（本例 18GB）、冷启动可接受 | **Deployment + emptyDir**（简单，重启冷缓存回源重建） |
| 单副本磁盘大（TB 级）、冷启动回源风暴代价高 | **StatefulSet + PVC**（缓存跨重启保温） |

本算例 18GB/副本较小 → **Deployment + emptyDir** 即可，但**必须前置一致性哈希**保命中率。

## 8. 最终结论与预管控建议

### 8.1 一句话推算逻辑（实测修正版）

> **先分工作负载类型 → 用「并发下载数 N」和「缓存失效天数 R」驱动规格；
> 但副本数 `K` 由「双上限」取大者决定。**
> - `N` 驱动 **连接数、副本数下限**：`FD=N×2`
> - `R` 驱动 **磁盘容量**：`Disk=d×R/0.8`
> - **副本数 `K = max(K_hit, K_cold)`（实测新增）**：
>   - `K_hit = B_in / P_hit`——稳态纯 HIT 吞吐需求（P_hit 实测单副本 ~数百 Mbps~Gbps，很宽松）
>   - `K_cold = 冷启动并发回源需求 / 单副本可承受回源并发`——**这才是通常的决定项**
>   - 实测证实：大文件场景 Squid 的 HIT 能力远大于回源能力，**瓶颈在回源/出口带宽而非 Squid CPU**

### 8.2 副本与配置预管控清单（实测校准版）

按算例（N=200, R=7天, H=0.85, SSL Bump）+ K8s 压测校准的预管控基线：

| 项 | 预管控值 | 依据（★=实测校准） |
|----|---------|------|
| 副本数 K | `max(K_hit, K_cold)`；本例取 8-12（含故障余量） | ★ 由冷启动回源并发决定，非仅 HIT 吞吐 |
| 单副本 CPU | **request 500m / limit 1-2 核** | ★ 按冷启动峰值配(实测冷启 CPU≈稳态2×)；稳态几十m |
| 单副本内存 | **request 512Mi / limit 1Gi** | ★ 实测全程<64Mi；比原估(2.5-4Gi)大幅下调 |
| 单副本磁盘 | 20 GB SSD（含 20% 余量） | `Disk/K` |
| `cache_mem` | 1 GB（内存宽松，可给足） | ★ 内存不是瓶颈 |
| `maximum_object_size` | ≥ 最大包/层大小（如 4 GB） | 否则大对象不缓存，出向省不下来 |
| 替换策略 | 磁盘 `heap LFUDA` | §2.3 |
| `max_filedescriptors` | ≥ 4096 | `N×2` + 余量 |
| 前置 LB | **一致性哈希/CARP**（去重保命中率） | §5 |
| 部署形态 | StatefulSet+PVC(要持久) / Deployment+emptyDir(追弹性) | §7.4 |
| startupProbe | TCP 3128，failureThreshold 大 | 覆盖缓存重建 |
| **出口/回源带宽** | **按冷启动全 MISS 峰值配**：≈ `N_cold并发 × 单流回源速率` | ★ 冷启动/缓存失效时的**第一瓶颈** |

### 8.3 四条硬性提醒（实测强化）

1. **副本数的真实决定项是「冷启动回源并发」，不是稳态 HIT 吞吐**（★实测修正）：
   Squid 纯 HIT 轻松扛数百并发流（CPU 几十 m），但**缓存失效/冷启动时全副本同时回源**，
   此时瓶颈在**回源并发能力与源站/出口带宽**。副本数与出口带宽都要按这个峰值配。
2. **副本数与一致性哈希绑定**：K 增大必须同时上一致性哈希，否则缓存重复→命中率崩、出向反弹。
3. **磁盘容量由「失效天数 R」定**：`Disk=d×R/0.8`。提命中率就加 R，代价是磁盘线性增长。
4. **CPU 是 SSL Bump 高并发 HIT 的真瓶颈、内存可省**（★N=120 补测修正）：
   开 SSL Bump 后，**高并发缓存命中的 TLS 加密才是 CPU 大头**——实测 N=120 HIT 打满 200m CPU，
   比同并发 MISS(88m)更吃 CPU。所以 **CPU limit 要按「高并发 HIT + 冷启动」双峰配足**，
   不能因"缓存命中"就低估 CPU。内存则相反：SSL Bump 下全程 <66Mi，limit 给 1Gi 足够，
   别按索引 15MB/GB + 大 SSL 余量高估。

### 8.4 校准

以上是**量级基线与推算链**。上线前用你的真实包大小分布/并发画像压测，校准两个最不确定的量：
**单副本可持续吞吐 `P`**（定副本数）和**实际命中率 `H`**（定出向带宽与磁盘容量）。其余参数随之收敛。

> Squid 性能对对象大小分布、命中率、是否 Bump、ACL 复杂度极敏感——报告给的是**推算逻辑与联动关系**，`P` 和 `H` 必须实测。

## 9. 实测校准（K8s 压测数据，2026-08-11）

在真实 K8s 集群用小规格摸上限（Deployment+emptyDir，SSL Bump 全解密，14MB RPM，
Job parallelism=N 并发），数据见 `../reports/stress-benchmark-20260811.md`。
以下用实测**修正/证实**前文推导逻辑。

### 9.1 证实的假设

| 前文假设 | 实测证据 | 结论 |
|---------|---------|------|
| B 类 crypto-bound，**CPU 非致命但是唯一瓶颈** | CPU 100m 档 N=40 被节流(耗时 33s→70s)；200m 撑到 N=80(峰值 129m)；内存全程 <64Mi，0 OOM | ✅ **CPU 是瓶颈，内存不是** |
| 副本线性扩展 | 2 副本 N=8 单流 min2.83s vs 1 副本 min1.47s，并发被分摊 | ✅ 线性成立，配合 ClientIP 亲和 |
| 冷启动出向冲高 | 冷启动 N=40 全 MISS，峰值 CPU **158m（≈稳态 2×）**，出向打满源站 | ✅ 冷启动余量必要 |
| 纯 HIT 单流吞吐 | 预热充分时 **18-41 MB/s（小规格）**；大规格前测 **90 MB/s** | ✅ 校准 `P_stream` |

### 9.2 修正的认知（重要）

**修正 1：瓶颈分两种，MISS 看源站、HIT 看 CPU（★N=120 补测关键发现）。**
- **MISS（冷启动/缓存失效）**：N 个并发同时回源被源站限速瓜分，Squid 等 I/O、CPU 空闲
  （N=120 MISS 时 CPU 仅 88m）。瓶颈在**回源并发与源站/出口带宽**。
- **HIT（高并发命中）**：Squid 要并发做 N 路 **SSL Bump 加密 + 读取大对象**，全是 CPU 密集。
  实测 **N=120 HIT 把 200m CPU 打满（199m）→ 反而比 MISS 慢（104s vs 67s）**。
  瓶颈在 **Squid CPU（SSL Bump TLS 加密）**。
→ **推导逻辑调整**：副本数 `K = max(K_hit_cpu, K_cold_egress)`：
  - `K_hit_cpu`：高并发 HIT 时 SSL Bump 加密的 CPU 需求（**开 Bump 时这常是决定项**）
  - `K_cold_egress`：冷启动全 MISS 时的回源并发/出口带宽需求
  - **关键**：开 SSL Bump 后，别再以为"缓存命中就省 CPU"——**高并发 HIT 的 TLS 加密是 CPU 大头**。

**修正 1b：真实混合场景 CPU 远低于纯 HIT 最坏情况（★随机包补测）。**
用 50 个真实 openEuler 包做 120 并发**随机下载**（模拟不同客户端下载不同包）：
- 稳态**混合命中率 ~67%**（缓存 1-2 轮填满后饱和），介于冷并发 55% 与全热 95% 之间。
- **CPU 116m**（混合 67% HIT），介于纯 MISS(88m) 与纯 HIT(199m) 之间，且靠近 MISS。
→ **规格策略**：**CPU limit 按纯 HIT 最坏情况（SSL 全加密打满）配足**，
但**日常混合场景（~67% HIT）只用约一半 CPU，有充足余量**。用纯 HIT 定 limit、用混合定 request。
→ **稳态命中率基线取 ~67%**（比理论值可信），代入 §7 出向带宽 `B_out=B_in×(1−0.67)`。

**修正 2：内存可大幅调小。**
前文 §4.2 `磁盘GB×15MB + cache_mem + SSL` 的 SSL 余量估偏大。实测 SSL Bump 全解密下内存全程
15-63Mi（含 64MB cache_mem），从未触及 128Mi。→ **内存 limit 按 `cache_mem + 磁盘索引 + 64Mi`
即可，SSL 上下文余量给 128-256Mi 足够**（除非缓存域名数极多）。

**修正 3：CPU 要按「冷启动峰值」而非「稳态」配。**
稳态纯 HIT CPU 很低（几十 m），但冷启动全 MISS+SSL Bump 时 CPU 冲到稳态 2×（158m vs 稳态~70m）。
→ **CPU limit 按冷启动峰值配，request 可略低**。

### 9.3 校准后的单副本承载参考（小规格外推）

| 配额 | 稳态可承载并发(纯HIT) | 说明 |
|------|-------------------|------|
| CPU 100m | 被节流,不足 | N=40 即劣化 |
| CPU 200m | ~N=80(峰值 129m) | 小规格甜点 |
| CPU 500m | 纯 HIT 41MB/s/流,冷启动峰值 158m | 冷启动更从容 |

外推：生产单副本给 **1-2 核**，纯 HIT 可支撑数百并发流；瓶颈会先出现在**回源并发/出口带宽**而非 Squid CPU。
