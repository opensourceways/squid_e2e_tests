# Squid 上限压测报告 — 2026-08-11

- 环境: K8s test-husheng, Deployment+emptyDir, 小规格摸上限
- 镜像: tommylike/squid-sslbump:latest (amd64)
- 测试文件: bcc-debuginfo 0.26.0 (~14.2MB RPM), SSL Bump 全解密
- 客户端: Job parallelism=N 并发下载

## 关键结论(剥离源站带宽变量后)

| 维度 | 实测 | 结论 |
|------|------|------|
| 纯 HIT 单流吞吐 | 18-41 MB/s (144-328 Mbps) | 小规格单副本单流能力 |
| CPU 瓶颈 | 100m 档 N=40 被节流(耗时33s→70s); 200m 撑到 N=80(峰值129m) | **CPU 是真实瓶颈** |
| 内存 | 全程 15-63Mi, 0 OOM/重启 | **内存极省, 非瓶颈, 可降到 64-96Mi** |
| 副本线性 | 2副本 N=8 min2.83s vs 1副本 min1.47s | 副本分摊并发, 趋势线性 |
| 冷启动 | 冷启 N=40 全 MISS, 峰值 CPU 158m(高于稳态) | 冷启动 CPU 冲高 + 打满源站出向 |

## 原始数据(stress-result.csv)

阶段 A(1副本 200m/128Mi, N 扫描):
- N=10: CPU 4m, 8s (源站限速, 非Squid瓶颈)
- N=20: CPU 4m, 17s
- N=40: CPU 64m, 33s
- N=80: CPU 129m, 65s ← CPU 接近 200m 配额

阶段 C(资源拐点, N=40):
- 100m/64Mi: CPU 被节流 45m, 耗时恶化到 70s ← 100m 不够
- 200m/128Mi: CPU 71m, 33s
- 500m/256Mi(预热充分): min0.65s 41MB/s ← 纯 HIT 上限

阶段 D(冷启动 500m/256Mi N=40): 全 MISS, 峰值 CPU 158m, avg 5s

## 校准要点(反哺 sizing 报告)

1. CPU 给足、内存可省: 小规格 CPU 200m 撑到 N=80, 内存 128Mi 用不到一半
2. 纯 HIT 单流 P_stream ≈ 18-41 MB/s(小规格), 大规格可达 90MB/s(前测)
3. 冷启动 CPU 比稳态高 ~2x, 出向打满源站 → 冷启动余量必要
4. 副本线性扩展成立, 配合 ClientIP 亲和去重
5. 源站带宽是外部硬约束: N 并发 MISS 时耗时随 N 线性增长, 与 Squid 无关
   → 生产真正要防的是"冷启动/缓存失效时的并发回源打满源站/出口"

## 补充测试: N=120 MISS vs HIT 资源对比 (2026-08-11)

用"少量 pod × 每 pod 多并发"模型(6 pod × 20/pod = 120), 对比冷/热两场景:

| 指标 | MISS(冷启动) | HIT(预热) | 关键发现 |
|------|-------------|----------|---------|
| 下载成功 | 120/120 | 120/120 | 均全成功 |
| 峰值 CPU | 88m | **199m(打满200m)** | ⚠️ HIT 反而打满 CPU |
| 峰值内存 | 51Mi | 66Mi | 均 <128Mi, 无 OOM |
| 平均耗时 | 67s | 104s | HIT 更慢(CPU 瓶颈) |

### 反直觉结论(重要修正)

**HIT 场景比 MISS 更吃 CPU**, 原因:
- MISS: 120 并发全在等源站回源(被限速), Squid 等 I/O, CPU 空闲(88m)
- HIT: 120 并发同时命中, Squid 要并发做 120 路 **SSL Bump 加密 + 读取 14MB**,
  全是 CPU 密集(TLS 加密) → **200m CPU 打满 → 成为瓶颈 → 反而拖慢到 104s**

### 系统极限定位

- 小规格单副本(200m CPU)的 **CPU 饱和点 = N≈120 HIT 场景**
- **SSL Bump + 高并发 HIT 是 CPU 真正压力源**, 比 MISS 更吃 CPU
- 修正前文"大文件瓶颈只在源站": 那只对 MISS 成立; **HIT 高并发下 Squid CPU 才是极限**

## 补充测试: 随机包下载(真实混合场景) N=120 (2026-08-11)

从 openEuler debuginfo 目录取 50 个真实包, 120 并发各自随机选包下载, 模拟真实生产(不同客户端下载不同包, 命中率非0非100%)。

| 轮次 | 本轮命中率 | 峰值 CPU | 峰值内存 | avg耗时 |
|------|-----------|---------|---------|--------|
| 轮1(冷) | 9% (HIT11/MISS109) | (采样错过) | - | 2.48s |
| 轮2(混合) | 67% | 97m | 35Mi | 4.81s |
| 轮3(混合) | 69% | 116m | 81Mi | 3.52s |

### 关键发现

1. **真实混合命中率稳定 ~67-69%**(50包/120并发)。缓存 1-2 轮即填满, 命中率从 9% 快速升到 67% 饱和。

2. **混合场景 CPU 落在纯 MISS 与纯 HIT 之间, 且靠近 MISS**:
   - 纯 MISS(N=120): CPU 88m (等源站)
   - 混合(67% HIT):  CPU 116m
   - 纯 HIT(N=120):  CPU 199m (SSL 加密打满)
   → **纯 HIT 是 CPU 上限最坏情况; 真实混合场景压力小得多(仅 116m)**。

3. **内存随缓存填充上升(35→81Mi)但仍 <128Mi, 无 OOM**。

4. **有失败(31-37/120)但均为源站小包/空包(size=0, 404)的 curl 非0退出, 非 Squid 故障**。
   → 生产监控要区分"Squid 故障"与"源站包不存在", 后者是正常 404。

### 对生产推导的意义

- **稳态混合命中率 ~67%** 是比理论值更可信的基线(介于冷并发55%与全热95%)
- **CPU 按纯 HIT 最坏情况(SSL全加密)配, 日常混合有充足余量**
- 失败率区分: 源站404 ≠ HA 失败
